# 29. Active Party (Party.activeUids) and Faint Tracking as Plain State

## Status

Accepted

## Context

A roster (`Party.pokemon`) is really a player's whole box — nothing in the app previously modeled the in-game rule that only 6 of them can actually be in the party and battling at once. That gap started to matter once battle logging needed to cover the common case of grinding EVs with a full active team: several Pokémon fighting (and earning EVs/Stat Experience) in the same battle, one of them fainting partway through a route, and a Pokémon Center visit clearing every faint at once before the next fight.

The natural first instinct was to log all of this — "which six are active," "fainted," "healed at the Center" — as roster events, the same way a battle or a level-up is (ADR 0006). That was rejected: none of it ever changes a recorded EV or Stat Experience value, and none of it is something a player would want to browse later in `<ev-history-log>`. ADR 0006 already drew this line for `nickname`/`nature`/`powerItem`: "attributes with no history of their own stay plain mutable state on purpose — event-sourcing those would be property-sourcing, not fact-recording." Which six Pokémon are active, and whether one of them is currently fainted, are exactly that kind of attribute — status, not history.

## Decision

1. **`Party.activeUids: string[]`** — the current active party, at most `MAX_ACTIVE_PARTY` (6) roster uids, ordered by when each joined. Plain state on the party, alongside `overrides`. A newly added Pokémon joins automatically while there's room (`addPokemon`); beyond that, membership changes via `Store#setActive(uid, active)`, which no-ops past the cap rather than bumping an existing member out — the UI decides who to bench first.
2. **`PersistedEntry.fainted: boolean`** — plain state on the roster entry, the same tier as `nature`/`powerItem`. Toggled via `Store#setFainted(uid, fainted)`; `Store#healParty()` clears it for every active-party member at once (a Pokémon Center visit). None of these three methods append a roster event or touch `evs`. `fainted` only means anything for the *current* active party, so `Store#setActive(uid, false)` (benching, including via a swap) heals it in the same call — there's nothing worth carrying across a bench, and a Pokémon comes back active healed regardless of how it left.
3. **Battle logging fans out per active participant.** `Store#logBattleForParticipants(uids, opponent)` records an independent `battle` event per selected, non-fainted uid — the same event shape and math `logBattle` already used for a single Pokémon, just called once per participant instead of introducing a new "multi-battler" event kind. `logBattle(uid, opponent)` itself is unchanged and still used by the Pokémon detail page's own single-mon battle button.
4. **Exp. Share skips a fainted holder, and is never double-granted to a battle's own direct participants.** `_applyExpShare` takes the set of uids already credited directly this battle (one uid for `logBattle`, the whole participant set for `logBattleForParticipants`) and excludes both those and any fainted holder — matching the games, where a fainted party member earns nothing and Exp. Share's passive grant only ever reaches Pokémon that didn't fight.
5. **The roster page (`#/parties/<slug>`), not a new route, hosts this — and is the *only* place active-party membership is managed.** An active-party grid sits under the party identity row: a responsive `auto-fill` layout of exactly `MAX_ACTIVE_PARTY` cells (more, comfortably-sized columns on a wide screen rather than a fixed count stretching into whitespace) — a card per active member (sprite, name, level or a "Fainted" tag, plus its own drag handle, swap, and faint/heal buttons) and a dashed "bring someone in" card per open slot. The roster card itself has no active-party control at all — every add/remove/swap/reorder action lives on the grid, so the roster card's row stays about the one thing it's for, EV tracking. "+ Log a battle" (multi-participant) sits in this section's own header next to a contextual "Heal at Pokémon Center" button; "+ Add a Pokémon" is the page's own top-nav-bar primary action (vacated once "Log a battle" moved down), both full-labeled buttons of equal weight. Opening "Log a battle" pre-selects only the lead (the first non-fainted active member) rather than everyone able — most battles are one Pokémon, so the rest of the participant strip stays opt-in.  The Pokémon detail page keeps its own single-mon "Log a battle" nav-bar button unchanged.
6. **Swapping is a dialog, not two round trips through the roster.** A filled slot's swap button, or an open slot itself, opens a picker (`#swap-dialog`) listing the bench; picking one calls `setActive` to bench the outgoing member (if any) and activate the incoming one in the same handler — no new store method, since `setActive` already does both halves atomically within one synchronous call. A filled slot's dialog also offers a plain "Bench — leave this slot open" option ahead of the bench list, since the roster card has no control of its own to fall back on.
7. **`Store#reorderActive(uid, toIndex)` reorders `Party.activeUids` itself**, independent of `reorderPokemon`'s reorder of the whole roster array. Order matters here beyond cosmetics — the first uid is the "lead," which is exactly what a fresh "Log a battle" pre-selects. Wired the same way the roster's own drag-to-reorder is (`lib/drag-reorder.ts`'s pointer-driven `wireDragHandle`, restricted to filled cards via `itemSelector`); its own e2e coverage only checks the handle renders and is wired, not the full pointer gesture — Playwright's synthetic mouse events land on it unreliably in this environment (`Store#reorderActive` itself has full, deterministic unit coverage instead).
8. **Picking an opponent applies immediately** — a separate confirm-then-apply step (tried and reverted) added a second popup on top of the opponent-search sheet for what's normally a single, fast action, and reopening the sheet to search again after a Cancel felt disjointed. The breakdown that step showed instead lives in two places, both inside the one sheet already open: `<pokemon-search>`'s `evModifier` hook — widened to accept a pre-formatted string, not just one `EvMap`, since a multi-participant breakdown doesn't fit that shape — drives each opponent suggestion's own row in the dropdown (`show-ev-yield`) with every selected participant's own `previewDefeat`-computed yield, live, before anything is picked; picking still applies immediately, and `logBattleForParticipants`'s return (`{ uid, applied }[]`) drives the same breakdown as the result status (`#add-status`) afterward. Both read `participantEvSummary`'s shared "Bulbasaur +1 HP · Charmander (no EVs — maxed)" formatting — a maxed-out participant reads as unambiguous fact rather than a single ambiguous count, before or after the fact.
9. **The participant selection never carries across an open/close of the sheet.** Opening always resets to just the lead; closing (`sheet-close`) clears the selection outright. A previous design carried the last selection forward "for convenience," but that meant reopening the sheet could silently apply to whoever was left checked from an unrelated earlier battle — starting fresh every time is the safer default, and most battles are one Pokémon anyway.
10. **`_normalizeEntries()` backfills both fields** for parties/entries saved before this shipped — `activeUids` fills up to the cap from the roster's own add order, `fainted` defaults to `false` — the same non-breaking-shape-drift mechanism every other field addition here uses (ADR 0009), no `SCHEMA_VERSION` bump. `applyImport` runs the same backfill after merging, so an older transfer payload lacking `activeUids`/`fainted` still lands in a consistent shape.

## Consequences

- The event log stays exactly what ADR 0006 intends it to be — a record of things that changed a Pokémon's stats — with no "Pokémon fainted" or "healed at the Center" noise to filter out later.
- Faint/active-party state is local device state like everything else non-event-sourced: it round-trips through Transfer (`activeUids` is exported/imported), but an existing local party's `activeUids` is left untouched by an import, the same way its nickname/nature/held item already are.
- A multi-participant battle costs one `battle` event per participant rather than one shared event — slightly more rows in `entry.events`, but each stays independently deletable/re-derivable exactly like a single-mon battle always was, with no special-cased "undo the whole group" logic needed.
- `<pokemon-search>`'s own blur-driven sheet-close (used by every `force-sheet` caller, not just this one) had to learn about `slot="sheet-extra"` content: tapping a participant chip moves focus to a light-DOM element the shadow-scoped check didn't recognize as "still inside the sheet," closing it out from under the user. The first fix (`this.contains(document.activeElement)`) overshot — once focus is anywhere inside an attached shadow root, `document.activeElement` retargets to the *host* itself, so that check was also true for the sheet's own close button, breaking it. The real fix scopes the check to this element's actual light-DOM children (`[...this.children].some(child => child.contains(document.activeElement))`), plus re-focusing the rebuilt chip after a selection re-render — narrow enough to protect slotted content without swallowing the component's own controls, for any future `sheet-extra` caller too.
