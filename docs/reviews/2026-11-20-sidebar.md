# Critical UI/UX review — sidebar first

Reviewed against commit d862b23 (v1.26.1), then the corrections in this change.
The sidebar is the primary scope, reflecting the user's clarification. Supporting
screens were sampled to compare patterns, not to claim an exhaustive app audit.

## Material findings and disposition

| Priority | Observed issue / user impact | Cause and remedy | Prevention / status |
| --- | --- | --- | --- |
| High | Current navigation used a large green pill plus darker left stripe. The user explicitly rejected this treatment. It made a location look like a selected data card. | Valid teal tokens were reused without checking their semantic role. Replace fill/stripe with normal ink, stronger text and a small trailing check. Remove the panel accent edge too. | ADR 0044 distinguishes location from data selection. Retain resting screenshots for Parties, current party and Settings separately. Fixed. |
| High | Title/Theme label and destination/helper text started on different left edges. | Dialog body padding and button padding compounded. Full-width rows now own one shared text gutter; header/context/Theme use the same value. | Runtime assertion compares actual text-start coordinates at 390px, 320px and desktop; it would fail the old insets. Fixed. |
| Medium | A party named Settings produced two unlabeled “Settings” destinations. | Dynamic party name replaced the destination's identity. Keep “Current party” and show the name beneath it. | A real-browser fixture reproduced the collision; a regression test now distinguishes the link from Settings. Fixed. |
| Medium | Theme arrow navigation dismissed the drawer and returned focus to Menu. This prevented comparing/adjusting options within the radio group. | Programmatic radio activation reused pointer close-after-pick. Keep keyboard/assistive activation in the group, moving focus with selection; Escape closes. | Keyboard test checks next-radio focus and drawer continuity; pointer selection retains its existing behavior. Fixed. |
| Medium | Narrow theme-control padding could drift from its intended layout. | A local single-class rule lost to the adopted shared button stylesheet. Use a scoped layout selector and inspect computed layout. | Screenshot and control-bound checks at 320px/150% text. Fixed. |
| Medium | Opponent-selection controls can retain an apparent pressed/focus state after touch. | WebKit retained :hover after tap, leaving a teal border.   edge assertion in Chromium and WebKit. The corrected right edge is preserved.

Inspected normal/current/hover states separately, plus empty data, populated
party, conflicting party name, Settings return, keyboard focus, 320px, desktop
and enlarged text. Heading, labels, descriptions and Theme now share a measured
edge. Theme control inner padding remains intentional. Touch targets stay at
least 44px. Native dialog dismissal and background inertness remain in place.
A visual checklist and shared tokens were insufficient previously because the
review never challenged state meaning or composed padding. AGENTS.md and ADR
0044 now require evidence for those relationships, not blanket claims of quality.

## Supporting app findings — not silently expanded into this change

1. **Medium: recipient recognition.** The defeat review shows sprites and levels
   without visible recipient names. This is observed in the six-participant
   screenshot; the risk of choosing the wrong Pokémon is an inference. Consider
   stable visible short names while preserving the user's no-count/no-jump rules.
2. **Medium: task wording.** Roster entry says “Log a battle”, sheet says “Record
   a defeat”, confirmation says “Log defeat”. Agree on one vocabulary across the
   entry, step and result; this is a consistency finding, not a data-loss bug.
3. **Low / design recommendation: guide discovery.** The training guide's first
   phone viewport is dominated by the training projection/table/chart; moves,
   matchups and training spots follow below. Consider flat section links or a
   task-oriented order. Do not add nested cards or assume user confusion was
   validated through screenshots alone.

These are review recommendations, not additional user commands or authorization
to redesign those flows in this batch. No usability testing with users or native
installed iPhone testing was performed. Existing fixtures mock API/competitive
content; their visual checks do not validate the external data itself.


## Opponent feedback evidence

WebKit reproduced the reported lingering border; Chromium touch did not. The
original border remained rgb(47,125,107) instead of rgb(230,226,218). The test now
passes without blurring controls or suppressing keyboard focus. [Touch release
screenshot](2026-11-20-sidebar/opponent-touch-release.png). This is touch-engine
emulation, not a physical iPhone validation. Shared button hover rules were also
gated so the same mechanism does not linger in the other shared controls.

## Validation

Final batch: 389 unit tests, typecheck, production build and the full 207-test
Playwright suite passed, including WebKit touch release and geometry checks.
The initial complete-suite attempt stopped before producing a summary; only the
subsequent confirmed 207-pass run is counted. Review document links and diff
